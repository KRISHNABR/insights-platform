# ADR-001 — Platform shape and reuse strategy: a versioned SDK, not a monorepo or a runtime service

**Status:** Accepted · **Date:** 2026-09-26
**Drivers from the brief:** *"the platform team is 2–3 engineers, who also maintain, upgrade, and
support everything they build"* · *"~5 consuming teams today, plausibly ~25 in two years"* ·
*"teams vary — some will ship interactive CRUD web apps; others, scheduled batch jobs."*

---

## Context

Five teams today, plausibly twenty-five in two years. Every one of them currently hand-rolls
auth, data access, deployment and logging. The platform's job is to stop that.

The constraint that decides this ADR is not scale — twenty-five is small. It is that **the
platform team is two to three engineers who also maintain, upgrade and support everything they
build.** Any mechanism whose cost grows linearly with tenant count will consume that team.

Two things can drift in a platform like this, and they are usually conflated:

1. **The library** — an app pinned to an old version of shared behaviour.
2. **The scaffold** — an app created eighteen months ago whose CI config and directory
   layout are eighteen months old, with nothing to tell anyone.

The second is the one most platforms lose, and the tell is easy to spot: an onboarding guide
containing a sentence like *"don't copy an existing app, use the current template."* That is a
rule standing in for a mechanism, and rules standing in for mechanisms decay.

## Decision

**Shared behaviour reaches apps as a versioned Python package, `insights-sdk`, living in its own
repository, installed as a dependency. Each tenant app is its own repository. Scaffolds are
generated by a CLI shipped inside the SDK, never cloned from a template repo.**

Tenant apps declare a **floor, not a pin**: `insights-sdk >=0.1,<1`.

The CLI ships *inside* the SDK distribution rather than separately, because the scaffold it
generates must be compatible with the SDK it targets. Versioned apart, you get scaffold/library
skew; versioned together, that is structurally impossible.

The upgrade story rests on seven mechanisms:

| # | Mechanism | What it buys |
|---|---|---|
| 1 | Semantic versioning, published artefact | Teams choose when to move |
| 2 | Floor not pin (`>=0.1,<1`) | Patches and minors flow with no tenant action |
| 3 | Expand / contract for breaking changes | New API added, old one kept working with a deprecation warning, removed later |
| 4 | **Deprecation telemetry** — the SDK reports its own version and which deprecated paths were hit | The platform sees *who is on what without asking*, so removal is evidenced rather than hopeful |
| 5 | SDK version surfaced per app in `insights status` | Version drift is a glance, not a survey |
| 6 | Release notes + an N-2 support window | Stops the team supporting five versions forever |
| 7 | `insights upgrade-scaffold` re-renders platform-owned files in a tenant repo | The scaffold gets an upgrade path, not just the library |

Mechanism 4 is the one that makes the rest safe. Without usage data, removing a deprecated API is
a guess; with it, it is a decision.

### How apps ship and run — the same decision, one layer down

The shape of the substrate is only half the question. The other half is how code gets onto it,
and it is answered the same way: **the platform owns the road, the tenant owns the vehicle.**

**Shipping.** A tenant's CI file is four lines and calls a central reusable workflow:

```yaml
jobs:
  deploy:
    uses: insights-hub/insights-platform/.github/workflows/deploy.yml@v1
    with: {app: headcount-dashboard}
```

Everything that happens on a push — manifest validation, entitlement checks against the registry,
the SDK support-window check, secret scanning, build, registration, rollout — lives on the
platform side. Improving any of it is one commit rather than twelve pull requests, which is the
same argument as the SDK and the reason both answers are in one ADR.

**Building.** A tenant has no Dockerfile. They declare `runtime.base` — one of a small published
family — and the platform renders the image. The base carries the runtime, the SDK, the non-root
user, the entrypoint and the health contract, so a platform CVE is one rebuild and a redeploy
rather than 25 pull requests. Nothing floats: a tenant cannot pin, and cannot drift.

**Running.** Two archetypes, one platform:

| | `kind: web` | `kind: job` |
|---|---|---|
| Started by | the runtime, on a port | the platform scheduler, from the registry and a cron line |
| Identity | per request, from the edge | per run — a service caller the scheduler constructs |
| Inherits | routing, sign-in, request ids, access logs, a health check that resolves every declared dataset | a run id, start/finish telemetry, SIGTERM draining, an exit-code contract |

`kind` selects a branch in a single `entrypoint.sh`, so the archetypes cannot drift apart, and a
team needing both writes two manifests rather than learning two platforms. What makes `kind` real
rather than decorative: a job **must** declare a schedule and a web app **must not** — the
manifest loader rejects either mistake. **Jobs are never deployed as services**; the registry
records the schedule and the platform runs them.

The deliberate omission here is retries, backfill and distributed locking in the scheduler. A
fancier scheduler is a component to be paged for, and nothing yet justifies one (ADR-005).

## The tension

**Tenant autonomy versus platform upgrade cost**, and they pull hard against each other.

A monorepo containing the platform and every app would make upgrades trivial: change the SDK, fix
every call site in the same commit, CI proves it. It was seriously considered and rejected for
two reasons. First, it **inverts ownership** — the platform team ends up editing, reviewing and
being blocked by code they did not write, and a flaky tenant test blocks a platform merge.
Second, the benefit is **weaker than it appears**: "we fix all call sites" works for a mechanical
rename, but any behavioural change still has to be reviewed and tested by the team that owns the
business logic. You get the blame without the clean win.

So we chose the harder upgrade path deliberately, and spent the design effort on making it
survivable. That is what the seven mechanisms are for.

## Alternatives considered

### A. Monorepo — platform and all tenant apps in one repository

**Genuinely attractive**, and the strongest case against our decision. Change the SDK, fix every
call site in the same commit, CI proves nothing broke. The upgrade problem largely disappears.

**Why not.** It inverts ownership: the platform team ends up editing, reviewing and being blocked
by code it did not write, and a flaky tenant test blocks a platform merge. And the benefit is
narrower than it looks — "we fix all call sites" holds for a mechanical rename, but any
behavioural change still needs review and testing by the team that owns the business logic. You
inherit the blame without the clean win.

*We would choose this instead if* all apps were built by one central team rather than by the
business teams that own the problems.

### B. A runtime platform service — apps call a sidecar or API for auth, data and telemetry

**The strongest rejected alternative.** Upgrades become instant and central: fix the service, every
app is fixed, no version drift at all. Enforcement is stronger too, because an app physically
cannot bypass a network call the way it can bypass a library.

**Why not.** It is an always-on, business-critical runtime that two to three engineers must
operate, patch and be paged for — plus a single point of failure for every tenant and a latency
hop on every request. The team that would have to run it is the same team onboarding
twenty-five tenants. We judged that the upgrade problem is cheaper to solve with process
(versioning, telemetry, deprecation windows) than the availability problem is to solve with
engineering.

*We would revisit this if* the platform team grew past roughly five engineers, or if SDK version
drift proved unmanageable in practice — which the status view is designed to tell us.

### C. A GitHub template repository

The common approach: tenants click "Use this template" and get a new repository.

**Why not.** It copies once and severs the connection. An app created eighteen months ago carries
an eighteen-month-old scaffold, and nothing tells the tenant or the platform team. The usual
compensation is a written instruction to always start from the current template — which is a
rule standing in for a mechanism. A generator can be re-run against an existing repo; a template
copy cannot.

### D. No shared code — a documented starter and copy-paste

**Why not.** This is precisely the status quo the brief describes: *"every team currently
hand-rolls the same things… slow, inconsistent, and increasingly hard to govern."* It also makes
every control in ADR-003 and ADR-004 unenforceable, because there is nothing central to enforce
them in.

### For the deployment half specifically

**E. Each team owns its own pipeline, with a documented recipe.**
Maximum tenant autonomy and zero platform maintenance — until a check has to change, at which
point it is twelve pull requests against code the platform team does not own, and the check is
optional in practice because nothing verifies it ran. It also removes the only place a rule can
sit that *must never ship* (ADR-004's CI layer). Rejected for the same reason as alternative D:
it makes controls advisory.

**F. A shared composite action or shared step, rather than a reusable workflow.**
Closer, and a reasonable halfway house. Rejected because a composite action is *invoked* by a
tenant-owned job — so the tenant still owns the job's structure, its triggers and the order of
steps, and can skip or reorder the platform's step. A reusable workflow owns the whole job.
The difference only matters when someone is under deadline pressure, which is exactly when it
matters.

**G. A full internal PaaS — push a branch, we detect and run it.**
The best tenant experience by a distance, and where this would go with more people. Rejected on
operating cost: build detection, buildpacks, a rollout controller and the support load of an
opaque "it didn't deploy" are a product, not a feature. The four-line caller keeps the tenant
experience nearly as good while leaving the mechanism legible, which matters when three people
have to debug it.

## Consequences

**What we now have to do**

* Operate a package index. Stubbed here as git tags; in production this is real infrastructure
  with its own availability story.
* Actually write release notes and hold the N-2 support window. This is a **process** cost
  falling on a small team, and it is the part most likely to slip.
* Build deprecation telemetry **before** we ever remove an API, or mechanism 3 is a guess.
* Own scaffold drift, via `insights upgrade-scaffold`. We took on a second upgrade surface.

**What gets harder**

* A tenant can pin an old version and fall behind. The status view makes that *visible*; nothing
  makes it *impossible*. That is a deliberate consequence of tenant autonomy.
* Cross-cutting changes now take weeks of calendar time rather than one pull request.

**What to watch**

* **The number of distinct SDK versions in production.** If more than three persist, the model is
  failing and the answer is either stronger CI enforcement of the floor or a move toward
  alternative B.
* Time between a deprecation being announced and the last tenant migrating.

## Revisit when

* **More than three distinct SDK versions persist in production.** The model is then failing in
  the way it is designed to fail — visibly. The answer is either stronger CI enforcement of the
  floor, or moving to alternative B, the runtime platform service.
* **A deprecation announced two release cycles ago still has users.** Mechanism 4 exists so
  removal is evidenced; if the evidence is being ignored, majors are unsafe to cut and the
  support window is fiction.
* **Cross-cutting change latency becomes the thing blocking the roadmap** rather than an
  acceptable cost. That is the monorepo trade reasserting itself, and it deserves a fresh
  argument rather than a reflex.
